## 一、P0：有具体证据的正确性风险

### P0-1　`LiveTvDirectRedirect` 的 `async void` Postfix → **真实竞态**

**位置**：`StrmAssistant/Mod/LiveTvDirectRedirect.cs:98-121`

```csharp
[HarmonyPostfix]
private static async void GetChannelMediaSourcesPostfix(Task<List<MediaSourceInfo>> __result)
{
    if (!IsEnabled || __result == null) return;

    try
    {
        foreach (var mediaSource in await __result)   // ← 第一个 await 就把控制权交回调用方
        {
            mediaSource.RequiresOpening = false;
            mediaSource.RequiresClosing = false;
            mediaSource.OpenToken = null;
            mediaSource.IsRemote = true;
            mediaSource.Protocol = MediaProtocol.Http;
            mediaSource.SupportsDirectPlay = true;
            mediaSource.SupportsDirectStream = true;
            mediaSource.SupportsTranscoding = false;
        }
    }
    catch (Exception e) { ... }
}
```

**问题**：`async void` 在第一个 `await` 处**立即返回**。Harmony 把原始 `__result` 交给调用方，调用方**可能已经开始遍历这个 List 并生成播放地址**，而此时 Postfix 的 `foreach` 还没跑到——`RequiresOpening=false` / `SupportsDirectPlay=true` 等字段**是否生效取决于线程调度**。

**症状**：Live TV 直链"时好时坏"、偶发仍走转码 / 仍要 OpenToken。

**修法**（项目里 `IsoExtraction` 已有标准范例，照抄即可）：

```csharp
[HarmonyPostfix]
private static void GetChannelMediaSourcesPostfix(ref Task<List<MediaSourceInfo>> __result)
{
    if (!IsEnabled || __result == null) return;
    __result = MutateAsync(__result);
}

private static async Task<List<MediaSourceInfo>> MutateAsync(Task<List<MediaSourceInfo>> task)
{
    var list = await task.ConfigureAwait(false);
    if (list != null)
    {
        foreach (var ms in list) { /* 同上赋值 */ }
    }
    return list;   // 关键：返回同一个 List，调用方拿到的就是改过的
}
```

**验证**：改完在 Live TV 频道页连点 10 次「播放」，看 `emby` 日志里是否稳定走 `DirectPlay`。

### P0-2　`MovieDb*` 补丁里 14 处 `.Result` 阻塞网络调用

**位置分布**（全部在 Harmony 补丁内，属刮削热路径）：

| 文件 | `.Result` 处数 | 阻塞对象 |
|---|---|---|
| `Mod/MovieDbEpisodeGroup.cs` | **10**（:166 :185 :218 :235 :263 :343 :370 :398 :407 :457） | `FetchLocalEpisodeGroup` / TMDB API |
| `Mod/OptimizeMovieDbEpisodeScraping.cs` | **4**（:79 :115 及配套） | TMDB API |
| `Mod/ExclusiveExtract.cs` | **1**（:194） | `Task.Run(() => GetStrmMountPath()).Result` |
| `Common/ImagePostProcessor.cs` | 2（:191 :360） | ffmpeg 进程 |
| `Common/IsoMounter.cs` | 3（:345 :354 :893） | 已带超时，可接受 |
| `Common/CommonUtility.cs` | 4（:94 :132 :136 :144） | 已带超时/连通性探测，可接受 |

典型形态：

```csharp
// MovieDbEpisodeGroup.cs:165
var episodeGroupInfo = Task.Run(
    () => Plugin.MetadataApi.FetchLocalEpisodeGroup(localEpisodeGroupPath),
    cancellationToken).Result;      // ← 阻塞线程直到磁盘/网络返回
```

**影响**：
1. 每个条目刮削都要同步阻塞一次 → **刮削任务吞吐直接按网络 RTT 打折**
2. 阻塞的是线程池线程 → TMDB 抖动时**线程池饥饿**，牵连 Emby 其它异步路径
3. `ExclusiveExtract.cs:194` 在**媒体探测热路径**上，探测一多就明显

**修法**（分两档，不必一次全改）：

| 档 | 范围 | 做法 |
|---|---|---|
| **必改** | `ExclusiveExtract.cs:194` | 该方法是 `void` Prefix，可改为把 mount 解析提前到 `IsoMounter` 侧（已有 `ResolveInProcessTitle` 缓存），Prefix 里**只读缓存不打网络** |
| **应改** | `MovieDbEpisodeGroup` 的 10 处 | 改为「换包」：Postfix 返回新 `Task`（`__result = WrapAsync(__result)`），把 `.Result` 换成 `await` |
| **可留** | `ImagePostProcessor` / `IsoMounter` / `CommonUtility` | 都有超时保护，且调用频次低 |

**收益量化建议**：改前后各跑一次「刷新 100 个剧集」任务，对比 `ExtractMediaInfoTask` 耗时与 `emby` 日志里的线程池告警。

### P0-3　`LibraryPathsInScope` 在 3 个类里**各自独立定义**

**位置**：

```
Common/FingerprintApi.cs:46          public static List<string> LibraryPathsInScope;
Common/LibraryApi.cs:273             public static List<string> LibraryPathsInScope;
IntroSkip/PlaySessionMonitor.cs:39   public static List<string> LibraryPathsInScope;
```

三份**互不引用**的静态可变 List，各自有自己的 `Update...()` 方法（`FingerprintApi.UpdateLibraryPathsInScope()` 等）。

**问题**：改配置（比如把片头探测范围从 A 库改成 B 库）时，只有被调用到的那个类会刷新 → **另外两处还是旧值**。表现为「设置改了但行为没变」「片头探测范围和声纹范围对不上」。

**修法**（成本极低）：

```csharp
// Common/LibraryApi.cs —— 唯一 source of truth
public static List<string> LibraryPathsInScope { get; private set; } = new();

// 其它两处改为只读转发
public static List<string> LibraryPathsInScope => LibraryApi.LibraryPathsInScope;
```

再在 `*OptionsStore.OnFileSaved` 里统一触发一次刷新。

**同类问题**：`LibraryApi.cs:274-278` 还有 `AllUsers` / `AdminOrderedViews` / `FirstAdminInternalId` 三个 `public static` 可变字段，建议一并收敛为 `{ get; private set; }`。

### P1-2　`Plugin.Instance` 770 次 —— 别大重构，新代码走注入

```
grep -c "Plugin.Instance" → 770
```

这是全项目最大的耦合面：任何类都能从全局单例拿 Logger、Options Store、LibraryManager。

**不建议大重构**（风险高、回归面大、收益慢）。务实策略：

1. **新代码一律构造注入**——项目里已经有正确范例：`IntroDbApi(IHttpClient, IJsonSerializer)`、`MetadataApi(...)`、`DoubanAssist(IHttpClient, IJsonSerializer, ...)`
2. **改动某个类时顺手把它的 `Plugin.Instance` 依赖收成字段**（童子军原则）
3. **只对"纯算法"类彻底去耦合**（`UdfTitleResolver` / `LanguageUtility` / `DolbyVisionProfile` 本来就该无依赖）——这也是 P1-1 能测起来的前提

## 三、P2：工程质量

### P2-1　`catch (Exception)` 194 处 vs 具体异常 32 处

插件里**宽 catch 是必要的**（单个条目失败不能拖垮 Emby），所以**不要减少宽 catch 的数量**。真正的问题是**分级不当**：155 条 `Debug` 里有一部分其实是"出错了但没人看见"。

**建议**：定一条明确规则并逐步套用——

| 场景 | 级别 | 要求 |
|---|---|---|
| 单条目处理失败，不影响其它条目 | **Warn** | 必须带 `item.Name` / `item.InternalId` |
| 补丁初始化失败（反射目标找不到） | **Warn** | 必须带类型名 + 缺失成员名（`ChineseMovieDb.cs:90-110` 已是好范例） |
| 可预期的外部因素（网络超时、404、风控） | **Info** | 带 URL 与状态码 |
| 真正不可恢复（数据库损坏、配置反序列化失败） | **Error** | 必须带 `e.ToString()` |

**快速检查点**：`catch (Exception e) { Logger.Debug(... e.Message) }` 这种形态（只记 Message 不记 StackTrace）应全部升级为 Warn + `e.ToString()`。

### P2-2　日志噪音：129 条 Info

生产环境里 `Info` 应该是「任务开始 / 结束 / 汇总」。逐条目循环里的 Info 建议降 Debug（用已有的 `Plugin.Instance.DebugMode` 开关门控）。

参考做法：`PatchBase.Initialize()` 里已经是这个模式（DebugMode 时打 Debug，否则打一行 Info）——把这个模式推广到批量循环即可。

### P2-3　`ContinueWith` 9 处 —— 异常不会传播

`Mod/ClearTagline.cs:61,73` 等：

```csharp
__result = __result.ContinueWith(t =>
{
    if (t.Status == TaskStatus.RanToCompletion) ClearTaglines(t.Result);
    return t.Result;
});
```

`ContinueWith` 会**吞掉原 Task 的异常**（`t.Result` 会重新抛，但若 `t` 是 Faulted 且没读 `t.Exception`，异常就变成 `UnobservedTaskException`）。且 `ContinueWith` 默认不继承 `TaskScheduler`，行为与 `await` 不同。

**建议**：改成 `async` + `await` 的换包模式（同 P0-1 的写法）。9 处一起改，半小时。

### P2-4　`Resources.Designer.cs` 靠手工同步 —— 根治它

**现状**：`PublicResXFileCodeGenerator` 是 **VS 设计期**生成器，`dotnet build` **不会**运行它 → 新增资源键后必须手工同步 `Resources.Designer.cs`，漏了会在运行时抛
`Cannot retrieve property 'X' because localization failed` → 页面直接 500。

已加 `tools/check_resx_keys.py` 做构建前校验（很好的兜底），但仍是"人工 + 检查"而非"自动生成"。

**根治方案**（成本中等，一次性）：

在 `csproj` 里加一个 `Target`，构建前用 `resgen`/`StronglyTypedResourceBuilder` 重新生成 `Resources.Designer.cs`：

```xml
<Target Name="RegenerateDesigner" BeforeTargets="BeforeBuild"
        Inputs="Properties\Resources.resx"
        Outputs="Properties\Resources.Designer.cs">
  <!-- 调 dotnet-resgen 或 MSBuild 内置 GenerateResource + StronglyTypedFileName -->
</Target>
```

**收益**：永久消除一类运行时 500 错误，且 `check_resx_keys.py` 可以退化成"双保险"。

## 四、明确**不建议**做的

| 项 | 为什么不建议 |
|---|---|
| **把 770 处 `Plugin.Instance` 全改成 DI 容器** | 风险高、回归面大、收益慢；渐进式即可 |
| **给 `LibraryApi` / `EnhanceChineseSearch` 做大拆分** | 这两个类虽然大，但**内聚度高**（都是"库查询" / "搜索索引"），拆开反而增加跳转成本 |
| **追求单元测试覆盖率数字** | Emby 类型 mock 成本极高；只测纯算法就够 |
| **把 `catch (Exception)` 换成具体异常** | 插件里必须兜底，换了会导致单条目失败拖垮整批任务 |
| **引入 DI 框架（Autofac 等）** | 插件生命周期与 Emby 冲突，收益不抵风险 |
