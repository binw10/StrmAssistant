## 三、已落地的改动（已编译 + 部署 + 实测，**未提交**）

只动了一个文件：`StrmAssistant/Mod/EnhanceChineseSearch.cs`（+203 / -7）。

| # | 改动 | 设计理由 |
|---|---|---|
| 1 | 新增 `_createConnectionManager` / `_managerId` 反射 | `Emby.Sqlite.PooledDatabaseConnectionManager.CreateConnection(bool, CancellationToken)` 是**所有连接唯一出口**，`public override` 且方法体大 → 不可能内联 |
| 2 | `PatchPhase1` 改为**双补丁**（仓库 + 管理器），任一成功即算成功 | 仓库侧负责提供 `DbFilePath`（定位 library.db），管理器侧负责覆盖全部路径；管理器补丁失败自动退回原行为 |
| 3 | postfix 兼容两种 `__instance` | 管理器没有 `DbFilePath`，用私有字段 `Id`（= 仓库类型名 `"SqliteItemRepository"`）判定是否条目库；`TargetException` 兜底 |
| 4 | **Phase2 搬出 postfix** → `QueuePhase2()`（`Task.Run` + 3s 延迟） | 写路径 postfix 持有 `_writeConnectionPool` 信号量 + 静态 `_lock`，在里面跑全量重建 = 全库冻结/死锁 |
| 5 | Phase2 改用**仓库的写连接** `CreateConnection(false, ct)` | 修掉"只读句柄重建必失败"（证据 B）；同时复用 Emby 写信号量，避免并发写撞 `SQLITE_BUSY` |
| 6 | 句柄级去重 `ConditionalWeakTable`（键 = `sqlite3` 句柄对象） | 克隆共享句柄 → 一个池位只需加载一次；省掉每次建连的 `simple_query` 探针。**只做加速**：表里没记录仍以探针为准，不会漏加载 |
| 7 | 每次新句柄打一条 Info：`tokenizer ready on <类型>(<库>) handle=... readOnly=...` | 原来关键分支只有 Debug（embyserver.txt 看不到），出问题无从排查 |

#### 为什么 v3 的方案能省 2/3 工作量

`DiscUtils` 拒绝构造的真正原因**不是不支持流**，而是流的 `Length` 只有 8MB：

```csharp
// DiscUtils.Udf.UdfReader 构造时会校验分区长度 ≤ 流长度
```

给它一个 **`Length` 正确、按需 Range 取数、可 Seek** 的流即可，**不需要自己解析 UDF extent**（项目已有 `DiscUtils.Udf 0.16.13`，已 ILRepack 进插件）。

#### 分四步落地

**ISO-1 `Common/HttpRangeStream.cs`（新增，约 200 行）**

```csharp
sealed class HttpRangeStream : Stream
{
    // 1) 总长：先 HEAD 取 Content-Length；不支持 HEAD 则 GET Range: bytes=0-0 读 Content-Range
    // 2) 块：1MB/块，Dictionary<long,byte[]> + LRU（上限 64 块 = 64MB）
    // 3) Read/Seek/Position：支持非对齐跨块读（DiscUtils 会从任意 offset 读）
    // 4) 容错：单块 3 次重试 + 空闲看门狗（复用 DownloadRange 的 20s 逻辑）
    // 5) 最终失败抛 IOException → 上层静默回退
}
```

关键约束：
- `Length` **必须是真实总长**（这是 DiscUtils 能否构造的唯一门槛）
- 只读、非线程安全（DiscUtils 单线程顺序访问为主）
- 服务器不支持 Range（返回 200 全量）→ 直接判定失败，不落盘

**ISO-2 `UdfTitleResolver` 加流重载（约 25 行）**

```csharp
public static TitleInfo Resolve(Stream stream, string label)   // 新增
{
    using var udf = new UdfReader(stream);   // 内部已有 Resolve(IDiscFs)
    return Resolve(new UdfDiscFs(udf));
}
```

**ISO-3 `IsoExtraction` 远程分支接章节（约 35 行）**

if (IsoMounter.TryNormalizeRemoteIso(inputPath, out var isoUrl))

#### 🔴 P1 的前置条件：进程内 UDF 一直是坏的（已修，`b0ffeab`）

建测试项目时顺手验了 `UdfTitleResolver.Resolve(path)`，发现它**永远返回 null**：

```
GetFiles('BDMV\PLAYLIST','*') => 0
pattern '*.*'                 => 1
pattern '*.mpls'              => 1
```

`UdfDiscFs.GetFiles` 用的是 `_udf.GetFiles(dir, "*")`，而 **DiscUtils 按 Windows 语义实现 searchPattern —— `"*"` 不匹配带扩展名的文件**。

- 影响：进程内 UDF 解析（Linux/Docker 无挂载时的唯一路径）**从未工作过**；Windows 上被挂载路径（`LocalDiscFs`）掩盖，所以一直没人发现
- 对 P1 的意义：**远程 ISO 章节正要复用这条路径** —— 不先修这个，P1 做出来也是死的
- 修法：改用 `GetFileSystemEntries` 全量列举 + `FileExists` 过滤（`UdfTitleResolver.cs`，10 行）

修完实测：真实 ISO 解析出 `BDMV\STREAM\00000.m2ts`（`00000.mpls`，30.7s，1 章节），与 `Chapters3` 落库结果一致。

## 五、我的建议

### 建议 1：先把 P0 提交掉（现在就可以）

改动已验证、可回退、只碰一个文件。建议提交信息：

```
fix(search): 修复写连接缺分词器导致元数据写入失败 + 索引重建跑在只读句柄
```

理由：这是"会静默毁数据"的 bug（元数据写入整体回滚），不值得等后续项一起发。

### 建议 2：P0.5 紧接着做，但单独一次提交

它依赖 P0 的修复才有意义（否则还原也会失败）。改动 15 行，风险极低。

### 建议 3：P1 单独开分支做，不要和 P0 混

理由：
- P1 是唯一大工作量项，且涉及网络/第三方协议（strm 代理、Range 支持情况千差万别）
- 它的失败模式是"章节取不到"（降级），P0 的失败模式是"数据写不进去"（灾难），两者不该绑在一起发布

### 建议 4：P2 测试项目插在 P1 之前

`HttpRangeStream` 的块边界/非对齐读是最容易出 bug 的地方，而它**完全不依赖 Emby**（纯 Stream 逻辑），用 xunit 测成本极低。建议 P1 开工前先建测试项目，第一个测试就是 `HttpRangeStream` 的块拼接。

### 建议 5：`DoubanAssist` 拆分最后做

它是 1936 行 God class，但**改它不会带来功能收益**，只是可维护性。等测试项目建好、P1 落地后再动，避免三个大改动互相干扰。

### 关于"要不要追 PRO 的剩余 3 项"

维持 v3 判断：G4（秒级追更）值得做、G2（启动清缓存）可做可不做、**G3（跨库播放进度）不碰**（动 `PresentationUniqueKey`，一旦出错用户数据会乱）。
