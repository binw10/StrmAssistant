#### 为什么 v3 的方案能省 2/3 工作量

`DiscUtils` 拒绝构造的真正原因**不是不支持流**，而是流的 `Length` 只有 8MB：

```csharp
// DiscUtils.Udf.UdfReader 构造时会校验分区长度 ≤ 流长度
```

给它一个 **`Length` 正确、按需 Range 取数、可 Seek** 的流即可，**不需要自己解析 UDF extent**（项目已有 `DiscUtils.Udf 0.16.13`，已 ILRepack 进插件）。

#### 分四步落地

**ISO-1 `Common/HttpRangeStream.cs`（新增，约 200 行）**

```csharp
sealed class HttpRangeStream : Stream
{
    // 1) 总长：先 HEAD 取 Content-Length；不支持 HEAD 则 GET Range: bytes=0-0 读 Content-Range
    // 2) 块：1MB/块，Dictionary<long,byte[]> + LRU（上限 64 块 = 64MB）
    // 3) Read/Seek/Position：支持非对齐跨块读（DiscUtils 会从任意 offset 读）
    // 4) 容错：单块 3 次重试 + 空闲看门狗（复用 DownloadRange 的 20s 逻辑）
    // 5) 最终失败抛 IOException → 上层静默回退
}
```

关键约束：
- `Length` **必须是真实总长**（这是 DiscUtils 能否构造的唯一门槛）
- 只读、非线程安全（DiscUtils 单线程顺序访问为主）
- 服务器不支持 Range（返回 200 全量）→ 直接判定失败，不落盘

**ISO-2 `UdfTitleResolver` 加流重载（约 25 行）**

```csharp
public static TitleInfo Resolve(Stream stream, string label)   // 新增
{
    using var udf = new UdfReader(stream);   // 内部已有 Resolve(IDiscFs)
    return Resolve(new UdfDiscFs(udf));
}
```

#### ✅ 实施结果（`5a60265`）

四步已全部落地，实测发现两处**必须补强**（原方案没考虑到）：

1. **只验 `Content-Length` 不够**。不支持 Range 的服务器照样回 `Content-Length`，但块请求会回 200 全量 → 流读不出数据还会白拉整个文件。
   → `TryOpen` 先 HEAD 取长度，再发一次 `bytes=0-0` **确认真的返回 206**。
   （这条是被测试逼出来的：`ServerWithoutRangeSupport_ReturnsFalse` 一开始是红的。）
2. **需要总预算**。远程解析会发多次块请求，慢链路可能把探测线程拖很久。
   → 加 90s 总预算，超预算 `FetchBlock` 返回 null（UDF 解析失败 → 静默无章节），并保留 3 次单块重试。

新增测试 7 例（总计 39 例全绿）：块边界跨读、非对齐 Seek、SeekFromEnd、流末尾返回 0、不支持 Range 返回 false、真实 ISO 经本地 Range 服务器解析出章节。

#### 🔴 P1 的前置条件：进程内 UDF 一直是坏的（已修，`b0ffeab`）

### 8.1 G4：追更最小等待改秒级

**语义**：条目入库后不足设定时间的**先不入队**，重新排到下个节流周期，好让首轮刮削先完成。
（`QueueManager.FilterByCatchupMinWait`，用 `item.DateCreated` 算年龄）

**关键设计**：老配置不能丢值。

```csharp
public int CatchupMinWaitSeconds { get; set; } = 0;      // 新，UI 可见
[Browsable(false)] public int CatchupMinWaitMinutes { get; set; } = 0;   // 旧，仅兼容
public int EffectiveCatchupMinWaitSeconds =>
    CatchupMinWaitSeconds > 0 ? CatchupMinWaitSeconds : Math.Max(0, CatchupMinWaitMinutes) * 60;
```

启动时一次性换算并**落盘**（`Plugin.Initialize`）：

```
TaskConcurrency - migrated CatchupMinWaitMinutes to CatchupMinWaitSeconds (600 s)
```

> ⚠️ 踩坑：`GeneralOptions.Initialize()` **只在设置页加载时调用**（`HomePageView:41`），
> 启动阶段不会执行。第一次实现把换算放在 `TaskConcurrencyOptions.Initialize()` 里，
> 结果内存值对了但 JSON 没落盘 → 用户下次打开设置页会看到 0。必须自己在 `Plugin` 启动路径里做。

**容差也要改**：原实现 `wait > 5s` 才 requeue，秒级设置下 5 秒以内的值会被完全吃掉（等于设了没用）。
改成 1 秒。

### 8.2 G2：启动时清空被动 TMDB 缓存

**语义**：TMDB 侧修正了某部片的信息后，让下次刮削立刻拿到新数据，而不是命中旧缓存。

`LocalMetadataCache.ClearPassiveCache()`：
- 只清 `<root>\cache`，**绝不碰** `override`（用户自定义）与 `patches`（合并补丁）
- 删文件后顺带清空目录，但保留 `cache` 根与三个类型目录（避免下次写入前目录缺失）
- 返回删除文件数，启动日志：`passive cache cleared on startup (21 file(s) removed)`

**边界**：选项只在缓存模式非 `None` 时可见；缓存根无效时跳过并记 Info。

## 七、P3 卫生项（✅ 已完成）

### 7.1 `Resources.Designer.cs` 漏同步 → 构建时自动修复

**问题**：Emby 的 `DisplayNameL` / `DescriptionL` 走**反射查 Resources 的公共静态属性**，而
`Resources.Designer.cs` 由 VS 设计期生成器产出，`dotnet build` 不会重新生成。往 `.resx` 加键却忘了同步 →
设置页 **500**（10-16 踩过一次）。原来的 `tools/check_resx_keys.py` 只**检测**、且 `ContinueOnError=true` 不阻断，
等于"提示了但没人看"。

**改法**：给脚本加 `--fix`，构建目标自动调用。

```xml
<Target Name="CheckResxKeys" BeforeTargets="CoreCompile" ...>
  <Exec Command="python ...\check_resx_keys.py --quiet --fix" ContinueOnError="true" ... />
</Target>
```

`--fix` 只做一件事：把「代码引用 + resx 有 + Designer 缺」的属性按 VS 生成器格式**追加**进 Designer
（幂等、保留 BOM、不动其它成员）。它**不会**新增 resx 键或编造译文——那两类仍然报 `[FAIL]`。

**踩到的坑（重要）**：目标最初挂在 `BeforeTargets="Build"` 上，**永远晚于编译**——
`Build` 的 `DependsOnTargets`（含 `CoreCompile`）先执行完才轮到 `BeforeTargets` 钩子。
所以修复必须挂 **`CoreCompile`**，否则就是"修了但编译已经失败"。

**验证**：手动删掉一个属性 → `dotnet build` → 输出 `[FIX] auto-added 1 missing property(ies) ...` + 编译成功；
恢复正常后输出 `[OK] resx keys consistent` 且文件无改动。

> 顺带把脚本的构建期输出改成 ASCII：原来中文在 MSBuild 的 GBK 控制台下是乱码（`[OK] 璧勬簮閿竴鑷?`），
> 关键标记 `[OK]` / `[FIX]` / `[FAIL]` 现在可读。

### 7.2 异常日志分级：约定 + 补漏

**结论：不做 121 处批量改造。** 审计后确认绝大多数静默 `catch` 是合理的（卸载、清理、缓存、取消检查），
把它们全升成 Warn 只会把日志刷满，反而降低信噪比。

只修「失败后用户可见症状、但日志里查不到原因」的几处：

| 位置 | 原状态 | 改为 |
|---|---|---|
| `HttpRangeStream.FetchBlock` 重试耗尽 | 直接 `return null`，无任何日志 | `Debug` 带块号 + 重试次数 + `e.Message` |
| `HttpRangeStream.FetchBlock` 服务器忽略 Range | 静默返回 null | `Debug` 带状态码 |
| `UdfDiscFs.GetFiles` / `GetFileLength` | `catch { }` 吞掉 | `Log(... + e.Message)` |
| `IsoExtraction` 章节注入失败 | `Debug`（embyserver.txt 看不到） | `Warn` + `Debug(e.StackTrace)` |

**约定（后续新代码遵循）**

| 级别 | 适用场景 | 写法 |
|---|---|---|
| **Error** | 用户可感知的失败 / 不可恢复 / 数据可能不一致 | 上下文（itemId 或路径）+ `e.Message`；`e.StackTrace` 走 Debug |
| **Warn** | 降级但可用（章节注入失败、某来源刮削失败、回退生效） | 一次一条，别在循环里刷屏 |
| **Info** | 状态变化、一次性决策结果 | **不要**用来记异常 |
| **Debug** | 预期内失败 + 可自愈（探针失败、best-effort 跳过、重试中间态） | 必须带 `e.Message`，不能只写 "failed" |

**两条硬规则**：
1. **宽 `catch` 可以保留，但至少留一条可诊断的日志**（不要空 `catch` 了事）。
2. `Logger.Debug` 在 `embyserver.txt` **看不到**（Emby 只收 Info+）→ **诊断期临时埋点必须用 Info**；
   常规 Debug 只服务"用户开了 DebugMode"的场景。
