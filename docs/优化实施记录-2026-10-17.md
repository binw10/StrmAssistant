## 批 5：多版本合并调研 + DoubanAssist 拆分评估

### B8. 427/428 未合并根因

- 427/428 类型为 Movie，PresentationUniqueKey 相同（`63e42d588dbc533e2f999960c8de9ea2`），MediaSources 互相包含——Emby 已在播放层将两者识别为同一视频的不同版本。
- 但 `MergeMultiVersionTask.ExecuteMergeMovies` 的查询条件包含 `HasAnyProviderId = {Tmdb,Imdb,Tvdb}`，而 427/428 的 ProviderIds 为空 `{}`，因此不会被纳入合并流程。
- `混合内容` 库（CollectionType=null）已被 `GetMovieLibraries()` 包含，库范围不是问题。
- **结论**：非 bug，属设计边界——无 ProviderId 的 Movie 不触发显式合并；PresentationUniqueKey 相同已保证播放层面多版本切换正常。如需合并，先完成元数据刮削使条目获得 ProviderId。

### B10. DoubanAssist 拆分评估

当前 `DoubanAssist.cs` 1925 行，职责混杂：
1. MdbList 评分更新（`UpdateMdbListRatingsAsync`）
2. 豆瓣搜索与匹配（`SearchByTitleAsync` / `GetSuggestionsAsync` / SPARQL）
3. 季映射（`RememberSeason` / `TryGetSeasonSubject` / 持久化）
4. 评分快照与持久化（`RecordRatingSnapshot` / `FlushRatings`）
5. 网页刮削 + V2 API 调用（`FetchSubjectAsync` / `FetchV2RatingAsync`）

**可拆方案**：
- `DoubanSearchService`：搜索、Suggest、SPARQL、`FetchSubject`
- `DoubanSeasonMapper`：季映射加载/保存/查找/清理
- `DoubanRatingService`：评分获取（网页+V2 API）、快照、刷盘
- `MdbListService`：MdbList 评分更新
- `DoubanAssist`：Orchestrator，组合调用

**风险**：
- 共享状态多（`_httpClient`、`cookie`、`cache`、` breaker`），拆分后需通过构造函数或选项对象传递
- 当前代码已通过主体校验等修改稳定，大重构引入回归风险
- 拆分收益主要为维护性，对功能无直接增益

**建议**：暂不实施，待新增豆瓣相关功能（如豆瓣评论、豆瓣想看列表同步）时再择机重构。

### 测试发现并修复的缺陷（均为实现时未暴露的真实 bug）

1. **A2-1 SQL 层排除**：任务取数查询 `HasAudioStream=false` 在 DB 层排除已有媒体信息的条目，内存标记检查永远收不到 → `Number of items: 0`。修复：取数后按标记 ID 用 `ItemIds` 查询补回。
2. **A2-2 DeserializeMediaInfo 捷径**：`HasMediaInfo(DB)` 为 true 直接 return true → 流程跳过探测与序列化（53ms 假完成）。修复：带标记条目跳过捷径。修复后实测 5.8s 真实 ffprobe → json 重新生成（4823B，与清理前一致）→ 标记消费清除。
3. **A4 聚合缺失**：404 实际走 `StatusCode==NotFound` 分支（原降级代码查异常消息永不命中）；刷屏主源是超时 catch（92 条 Warn/任务）。修复：失败分类计数 + 首条 Warn + 收尾单行汇总。

### 部署与验证经验

- .NET 用户字符串堆为 UTF-16LE：二进制校验 DLL 功能必须用 `utf-16-le` 编码，UTF-8 检查会全部误报缺失。
- 插件 JS 实际服务路径：`/web/components/strmassistant/strmassistant.js`。
- Emby 4.10 web 登录态注入（localStorage `servercredentials3`）用管理员 API key 无效：连接管理器校验 token 与用户绑定关系（`afterConnectValidated` → ServerSignIn），UI 交互实测必须用真实用户凭据（AuthenticateByName）。
