# 0001 · 不合并上游分支，只按项移植

- **状态**：✅ 已采纳
- **日期**：2026-10-22（复核）
- **相关**：[../architecture/emby-version.md](../architecture/emby-version.md)

## 背景

本仓 `myp015`（StrmAssistantPlus，3.0.0.58）与上游 `OneManJS/StrmAssistant:main`（2.3.0.0）
分叉于 `668c381`（2025-12-03）。到 2026-10-22 为止：

| | 本仓 | 上游 main |
|---|---|---|
| 提交数 | 195 | 8 |
| 最新 | 2026-10-21 | 2026-05-10 |
| 版本 | 3.0.0.58 | 2.3.0.0 |

上游那 8 个提交（`f238271` … `f8baae4`）共 2521 行有效新增。

## 决策

**不 merge、不 rebase。需要什么就单独移植。**

## 理由

1. **SDK 会回退**：上游把 `mediabrowser.server.core` 从 `4.9.1.90` 降回 **`4.8.10.0`**，
   还加了 `SQLitePCLRaw.core 1.1.14`。合并 = 回退我们的 Emby 支持基线。
2. **带了二进制**：上游把 `StrmAssistantPro.dll`（约 5MB）提交进仓库。不该进源码树。
3. **36% 的内容我们已经有**：实测上游 2521 行有效新增中 905 行已在本仓
   （`Core/MemoryCleaner.cs` 逐行相同、`OptimizeMovieDbEpisodeScraping.cs` 96%）。
   之前的移植已经做过了。
4. **核心文件已分叉到无法合并**：`EnhanceChineseSearch.cs` 我们 1691 行、上游 2402 行，
   索引架构不同；`Plugin.cs` 差异 773 行。合并等于手工重写。
5. **版本号冲突**：上游是 2.3.0.0，我们是 3.0.0.58。

## 后果

- 每次上游更新，需要人工逐项评估（约 1 小时），按"能独立移植 / 已有 / 不做"三分类。
- 移植时**不照抄**，要按我们的架构改造。已知上游有两处不能直接抄：
  - `LibraryApi` 的排除项缓存只按设置字符串做 key，漏了 `EnableIsoExtraction`；
  - `QueueManager` 换了 `SemaphoreSlim` 却不 Dispose 旧的，我们保留原实现。
- 2026-10-22 的移植结果见 `history/2026-10/2026-10-22-*.md`（P1/P3/P6 已落地，
  P2/P4/P5 待排期，G3 类跨库进度明确不做）。
