## 一、0-A 豆瓣客串演员中文化（对齐 PRO .55 S5）

### 改动
`StrmAssistant/Provider/Douban/DoubanAssist.cs` — `ApplyCastChineseNamesAsync` 的过滤条件：

```csharp
// before
p.Type == PersonType.Actor && !string.IsNullOrWhiteSpace(p.Name)
// after
(p.Type == PersonType.Actor || p.Type == PersonType.GuestStar) && !string.IsNullOrWhiteSpace(p.Name)
```

`PersonType` 经 `ilspycmd` 实证为**普通枚举（非 flags）**，故必须显式 `||` 列出，不能指望位运算。

### 与 v9 方案的偏差（有意）
v9 方案列的「配套」项 —— 把 `CelebrityRoleRegex` 从 `饰[:：]` 扩到 `饰|客串|嘉宾` —— **未实施**。
原因：`DoubanCelebrity.Role` 字段**全仓只写不读**（仅 `DoubanAssist.cs:688` 赋值，无任何读取点），
改正则对行为零影响，属纯噪声改动。

### 验证与阻塞
- **数据面（已证）**：`library.db` 的 `ItemPeople2` 表按 `PersonType` 统计 —— Actor(0)=546、**GuestStar(4)=62**、Director(1)=25、Writer(2)=19、Producer(3)=6、Composer(6)=4。
  即库内确有 **62 条客串人员**，修改前它们全部被跳过。样例：item 80 的客串为 `Kofi Musah` / `Kabir Sharma` / `Trent` …（均纯英文名，正是待中文化对象）。
- **端到端受阻**：豆瓣 `GET /subject/{id}/celebrities` 在**无 Cookie** 时返回
  `302 → https://sec.douban.com/c?...`（风控页），插件亦识别该页并 `RegisterBlocked`。
  因此本环境无法产出 `DoubanAssist - Cast X -> Y` 日志行。需配置已登录 `DoubanCookie` 才能做真机端到端验证。
- 代码层：`dotnet build -c Release` 0 错误。

## 二、0-B 多版本 `MediaInfoExtended`（对齐 PRO .55 S3）

### 标签格式
`BuildMediaInfoLabel(video, bitrate, size)` = 画质档位 + 编码 + 码率 + 体积，缺项自动省略：
- 全项：`4K HEVC 46.1Mbps 168.4MB`
- 无高度/无视频流（strm 未探测）：`64.4Mbps 8MB`

> 设计取舍：**「画质」（MediaInfo）保持只输出档位**（`4K`/`1080p`），不改动既有行为；
> 仅新选项输出复合串，零回归。这是与 PRO 语义的差异（PRO 的 MediaInfo 本身已含码率）。

### 前端排序修正（必要，非可选）
`Web/Resources/strmassistant.js` 的 `scoreOf` 用 `rankOf(labels, label)` 做**精确串**匹配画质档位。
复合标签整串匹配不到 → 返回 `-1` → 被判最低档。故改为取首个空格分词：

```js
const rawLabel = info.Label || info.label;
const label = rawLabel ? String(rawLabel).split(' ')[0] : rawLabel;
```

档位词因此**必须留在标签首位**（已在服务端注释中标注该契约）。
